# 部署与备份

## Windows 本机

安装 Python 3.13 与 Node.js 22.14+，运行根目录“安装与构建.ps1”。实际本机已准备独立 .venv、前端依赖及构建。

deploy/local_postgres.py 从 EDB 官方二进制地址准备 PostgreSQL 18.6-1，仅解压 bin/lib/share，在 .runtime 保存来源与 SHA-256。只监听 127.0.0.1:5544，使用 SCRAM；不安装系统服务。业务角色 ep_app 非超级用户。PostgreSQL 管理凭据和应用 DSN 在当前用户及 SYSTEM 可读的 .local 中；不要发送或提交。

启动“打开企业工作台.cmd”。服务只在 127.0.0.1:8774，工作区是本目录 workspace。首次链接在 workspace/.local/first-login-url.txt，通过片段传递设置凭证，页面立即移除片段。本人创建账号；没有默认密码。停止工作台应使用正常进程管理；停止本项目数据库可运行 .venv/Scripts/python.exe deploy/local_postgres.py --stop，先确认工作台不再处理任务。

若同端口已有其他服务，不改安全校验或占用其他项目。v2.0 用 8772、v3.0 用 8773，本企业版用 8774。

## PostgreSQL 与文件成套备份

运行：

.venv/Scripts/python.exe deploy/backup.py backup --config .local/config.json --path "全新备份目录"

.venv/Scripts/python.exe deploy/backup.py verify --path "备份目录"

备份持有业务事务锁，用 pg_export_snapshot / pg_dump 获得一致数据库快照，再复制所有登记的不可变文件，生成 SHA-256 清单。备份目录必须全新，失败后不得把部分目录当成功备份。

备份包含私有工程、实名记录与密码哈希，按受限资料保管；不包含数据库连接密码或模型 Key。测试备份只能用 .qa/config.json。备份与 QA 文件不进入源码包。

恢复需事先准备一个空 PostgreSQL 数据库和指向全新制品目录的私有配置，再运行：

.venv/Scripts/python.exe deploy/backup.py restore --config "新目标配置" --path "已校验备份目录"

程序拒绝覆盖已有工作区、非空数据库或跨 QA／生产数据域恢复。恢复移除登录会话、撤销任务授权、提升权限纪元，queued/running 工程或模型任务标为 unknown；不派发任务。随后用原账号登录，人工核查工程及审批范围。原备份、旧目录和旧数据库保留。

本机已对独立 QA 库完成备份、摘要校验及新空数据库／新目录恢复。生产恢复演练需工厂另行使用真实备份验收。

## Docker 候选入口

当前机器未安装 Docker，以下文件尚未经过构建与运行验收，不宣称部署成功。

先用 Python 环境运行 deploy/prepare_docker.py，生成 .deployment 下两个独立数据库密码文件及空模型 Key 文件。若需厂内模型，将 Key 写入该受限文件，并通过 EP_MODEL_KEY_BASE_URL 明确绑定端点。

docker compose up --build --detach --wait

docker compose exec -T workbench cat /data/workspace/.local/first-login-url.txt

第二条只在本机终端查看；不要复制到日志、报告或聊天。入口仍为 127.0.0.1:8774。数据库不向宿主机发布端口。应用使用非 root、只读文件系统、cap_drop 与 no-new-privileges；制品和 PostgreSQL 分别持久化。宿主机端口不得改成全网监听；Host/Origin/会话/CSRF 仍有效。

.dockerignore 为源码白名单，不能把 workspace、.qa、.local、.runtime、案例、密钥、备份或嵌套发布包加入上下文。Docker PostgreSQL 初始化创建独立非超级用户 ep_app。容器不执行 Windows GX 编译或现场操作。
